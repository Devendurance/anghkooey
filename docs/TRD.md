# ANGHKOOEY — TECHNICAL REQUIREMENTS DOCUMENT (TRD)

**Version:** 1.0 · **Date:** 8 October 2026 · **Status:** Proposed implementation contract  
**Scope:** Production-shaped 10-hour hackathon MVP · **Primary model:** DeepSeek Flash · **Memory network:** Walrus Mainnet · **Messaging:** Photon Spectrum (Telegram + iMessage)

> **Engineering rule:** Real Mainnet memory is the system's source of durable personal facts. SQL may hold identity, job state, links, provenance identifiers, and short-lived conversational context; it must never silently substitute for Walrus as the persistent personal-preference store.

## 1. Technical goals and constraints

- TypeScript-first codebase; runnable by a second builder from a public README.
- One shared conversation pipeline called by web and Photon channel adapters.
- Real, reproducible `remember → wait for Mainnet job → blob ID → new session recall`.
- Three isolated real users, ≥10 successfully persisted facts/blobs each.
- A linked person can continue conversations across **Web, Telegram, and real iMessage**.
- Correct/stale memory handling, transparent provenance, no cross-user leakage.
- No bookings, real-time rates, hotel availability, live data scraping, or payment workflows.
- User-visible memory saves must not lie about pending/failed jobs.

## 2. Recommended stack and package decisions

| Concern | Default choice | Rationale |
|---|---|---|
| Language/runtime | TypeScript strict; Node.js 22 LTS or another tested supported Node version | Shared types; supports Next.js + Spectrum server |
| Web UI | Next.js App Router, React, Tailwind CSS | Quick deployable mobile-first UI |
| Web hosting | Vercel **or** any Node-capable web host | API routes can handle web chat; no long-running stream on Vercel Functions |
| Messaging process | **Always-on Node worker** on VPS/container host | Photon Spectrum has a persistent inbound message loop; should not live inside a short-lived serverless handler |
| Channel SDK | `spectrum-ts`; `imessage` + `telegram` provider modules | Official shared Photon agent abstraction |
| Durable memory | `@mysten-incubation/memwal` production managed-relayer client | Official Walrus Memory SDK; no custom vector store in MVP |
| LLM | DeepSeek API (`https://api.deepseek.com`, `deepseek-flash`) | Eligible alternative primary model; documented API compatibility |
| SQL metadata | Existing Neon/Postgres or equivalent Postgres instance, `postgres` or `pg` driver | Simple durable identities, tokens, delivery idempotency, blob bookkeeping |
| Input validation | `zod` | Validate model output and inbound requests |
| Tests | Vitest + Node integration scripts | Focused tests and live smoke script |
| Monitoring | Structured console logs + simple health endpoints | Minimal setup, sanitized, enough to debug blockers |

**Avoid dependencies that don't serve a P0 requirement.** Do not introduce a vector database, Supabase Auth, Redis, payment SDK, hotel search API, queue service, or agent framework just to look sophisticated.

**Important runtime distinction:** Pi + Muse Spark Contributor is the *coding assistant*. The deployed chatbot's responses are generated by **DeepSeek Flash**. Document both separately, and do not claim Pi/Muse Spark is the deployed bot model.

## 5. Database: identity and delivery metadata only

### Minimal tables

| Table | Columns (minimum) | Rules |
|---|---|---|
| `users` | `id UUID PK`, `created_at`, `consent_at?` | Stable app user ID; non-reversible unrelated to usernames |
| `web_sessions` | `id`, `user_id`, `token_hash`, `expires_at`, `created_at` | Secure, HttpOnly/SameSite cookie; no passwordless identity guesswork |
| `channel_identities` | `id`, `user_id`, `provider`, `provider_sender_id`, `verified_at`, `created_at` | Unique `(provider, provider_sender_id)`; never identify by display name |
| `link_tokens` | `id`, `source_user_id`, `token_hash`, `expires_at`, `used_at`, `pending_target`, `confirmed_at` | 128-bit+ random entropy; hashed, TTL, one use, explicit confirmation |
| `conversation_sessions` | `id`, `user_id`, `channel`, `created_at`, `ended_at?` | New session must not inherit a full old transcript |
| `recent_messages` | `id`, `session_id`, `role`, `text`, `created_at`, `expires_at` | Short-lived (e.g. 24h/7d) local context only, with deletion/retention policy; avoid persistently caching personal profile content |
| `memory_jobs` | `id`, `user_id`, `namespace`, `job_id`, `status`, `blob_id?`, `submitted_at`, `completed_at?`, `error_code?` | Records actual Mainnet write jobs and outcome; no duplicate claims |
| `memory_metadata` | `blob_id PK`, `user_id`, `memory_key?`, `category?`, `supersedes_blob_id?`, `state`, `created_at` | **No personal fact text required**; use for supersession/provenance |
| `inbound_events` | `provider`, `provider_event_id`, `processed_at`, `status` | Unique idempotency guard prevents duplicate reply/write |

SQL table `memory_metadata` is *metadata*, **not a second memory engine**. The actual content and semantic recall must come from Walrus. Avoid saving personal user statements in analytics or persistent audit tables. The short-term message cache should expire, and public README must accurately describe retention.

### Namespace contract

```ts
function namespaceFor(userId: string): string {
  // userId is a server-issued, validated UUID from authenticated context.
  return `anghkooey:v1:u:${userId}`;
}
```

- **Never** accept `namespace`, `user_id`, or `provider_sender_id` from arbitrary client JSON as authorization.
- MemWal isolation is `(owner, namespace)`: in the MVP, the app may use one custodial Walrus account and one delegate key, but distinct **flat, exact-match namespaces** for app users.
- A single app-owned MemWal account means memory is **not yet individually user-custodied**. Do not market it as self-sovereign unless the design changes.
- All three channels must resolve to one canonical user UUID *after verified linking*; before linking they must remain separate.

## 6. Walrus Memory SDK integration contract

Current public SDK usage, subject to validation against the exact installed version:

```ts
import { MemWal } from "@mysten-incubation/memwal";

function createMemoryClient(namespace: string) {
  return MemWal.create({
    key: process.env.MEMWAL_PRIVATE_KEY!,
    accountId: process.env.MEMWAL_ACCOUNT_ID!,
    serverUrl: process.env.MEMWAL_SERVER_URL ?? "https://relayer.memory.walrus.xyz",
    namespace,
  });
}

async function saveDurableFact(userId: string, fact: string) {
  const namespace = namespaceFor(userId);
  const memwal = createMemoryClient(namespace);
  const written = await memwal.rememberAndWait(
    fact,
    namespace,
    { timeoutMs: 30_000 },
  );
  // Persist written.job_id + written.blob_id only after success.
  return { namespace, jobId: written.job_id, blobId: written.blob_id };
}

async function recallFacts(userId: string, query: string) {
  const namespace = namespaceFor(userId);
  const memwal = createMemoryClient(namespace);
  const result = await memwal.recall({
    query,
    namespace,
    limit: 8,
    maxDistance: 0.7,
  });
  // Apply known superseded/tombstone metadata before model context injection.
  return result.results;
}
```

**Source:** https://github.com/MystenLabs/MemWal/blob/dev/SKILL.md. SDK returns `{ results: [{ blob_id, text, distance }], total }`; `rememberAndWait` provides `blob_id` on completed write.

### SDK behavior that the implementation must respect

1. **Append-only semantics:** `remember` creates a new record. It does not upsert by preference key. Duplicate requests can create duplicate Mainnet blobs.
2. **Async indexing:** A newly accepted write may not be immediately recalled; use `rememberAndWait` / `waitForRememberJob`, not a UI-only delay or arbitrary assumption.
3. **No default recall threshold:** nearest memories can be irrelevant. Use `maxDistance` and app-level filtering; tune with real tests instead of treating `0.7` as an infallible truth boundary.
4. **Flat namespace:** no hierarchical prefix queries; exact string equality matters.
5. **Current forget semantics:** the relayer's forget endpoint may remove index rows while underlying Walrus blobs persist until expiry. Do not promise instant permanent erasure or implement undocumented SDK methods.
6. **Failure handling:** job timeout ≠ confirmed failure or success. Persist pending state, query status through supported APIs, and avoid duplicate write retries until state is resolved.
7. **Agent ID evidence:** record the Walrus Memory account/agent identifiers requested by the submission form and a verified unique Mainnet blob count. Do not infer a count from chat messages.

## 7. End-to-end chat orchestration

One shared `handleMessage({ canonicalUserId, channel, sessionId, messageId, text })` implementation must perform:

1. **Authenticate and authorize** internal user based on cookie/provider-originated sender identity.
2. **Idempotency check** (channel + provider message ID or web request ID) and rate limit/length validation.
3. **Classify intent**: discuss/request advice, new durable fact, correction, “what do you remember?”, account/link command, or unsafe input. A single text can have multiple intents.
4. **Retrieve relevant Walrus memories** for advice requests *before generating*; apply distance + known supersession metadata.
5. **Build bounded prompt** from system rules, current message, last few same-session turns, and verified relevant memory records with `blob_id`/provenance. Never include another user's context.
6. **Call DeepSeek Flash** through server-side API; parse structured extraction separately or via validated JSON output. Never trust raw model function arguments without schema validation.
7. **Save qualified, consented, non-sensitive distilled memory facts** via Walrus and record confirmed blob IDs. For corrections, include a new fact and record relationship to stale blob metadata.
8. **Return answer + memory receipt sources + save status**. If provider messaging cannot render rich UI, turn status into brief human-readable text.
9. **Record sanitized telemetry**: trace ID, channel, response outcome, latency, memory job state, retrieved blob IDs (not personal content), model ID.

### Fact extraction policy

- Model may propose **0–3 durable facts per message**. Validate exact fields through Zod: `text`, `category`, `scope` (`durable | trip_specific`), `memory_key`, `confidence`, `sensitive`, `correction_of?`.
- Re-serialize trusted output before saving; never allow the model to choose namespace or write credentials.
- Persist a fact only when directly stated or explicitly confirmed, relevant to stays/travel/dining, not a secret/sensitive category, and not already known as identical to a saved fact.
- Prefer **one distilled statement per blob** (easy to prove ≥10 meaningful memories) but avoid gaming counts by splitting a single fact into meaningless fragments.
- Example fact text: `Preference: quiet hotel rooms over central locations. Reason: a prior busy-road hotel prevented good sleep. Stated by user; current as of 2026-10-08.`
- Temporary trip details should be tagged for context, not silently treated as lifelong preferences.
- If the model refuses/returns invalid JSON, skip memory capture safely; still answer the user's question when possible.

### DeepSeek API usage

Official base URL: `https://api.deepseek.com`, model: `deepseek-flash`; either official HTTP call or OpenAI-compatible client is acceptable. When using `response_format`/tool calls, validate JSON and inspect error modes. The primary response-generating in-app model must remain **DeepSeek** for intended category eligibility. Document actual model string/version/runtime and fallback if changed.

Reference: https://api-docs.deepseek.com/

## 8. Memory revision and correction algorithm

**Problem:** Walrus SDK `remember` is append, not replace; semantic recall can surface an earlier contradictory statement.

**MVP strategy (application-level, no fiction about native upsert):**

1. On new statement “I now prefer X,” classify `memory_key` (e.g., `stay.noise_preference`) and explicit revision intent.
2. Find any known active prior blob IDs for the user's same memory key in `memory_metadata`. If none, look up relevant Walrus recall hits and allow user confirmation if uncertain.
3. **Write corrected memory to Walrus and wait for completed blob ID first**. Example: “Current preference: quiet rooms, upper floors preferred, breakfast no longer required (updated Oct 8).”
4. In one SQL transaction set older matching blob metadata `state='superseded'` and add new blob ID as active. On write failure, **do not retire old preference**.
5. During retrieval, discard known superseded blob IDs. Because semantic retrieval is top-K, request enough candidates to leave relevant active results after filtering; don't just rely on one old nearest match.
6. If older memories lack metadata (e.g., created before tracking), ask a clarifying question when results conflict rather than silently deciding.
7. **Test both** correction immediately after write and after an entirely new session.

**Limitation:** Without a true Walrus update/delete primitive, superseded underlying blobs still exist; the app ensures it won't *use* known stale blobs as active profile facts. If a user asks to delete, provide technically accurate scope and duration rather than pretending an immutable blob vanished.

## 9. Photon Spectrum integration

Photon's public TS SDK uses a shared long-running message stream. Exact event shapes must be checked against installed package types:

```ts
import { Spectrum } from "spectrum-ts";
import { imessage } from "spectrum-ts/providers/imessage";
import { telegram } from "spectrum-ts/providers/telegram";

const spectrum = await Spectrum({
  projectId: process.env.PHOTON_PROJECT_ID!,
  projectSecret: process.env.PHOTON_PROJECT_SECRET!,
  providers: [imessage.config(), telegram.config()],
});

for await (const [space, incoming] of spectrum.messages) {
  // Adapter must resolve verified sender + unique message ID using actual SDK types.
  // Run shared handleMessage(), then send via space.send() for portable delivery.
  // Add catch/retry isolation around each message so one failure doesn't kill the loop.
}
```

- Use a **real Photon Cloud iMessage line** and a real Telegram bot/provider setup. Saving a configuration file is not equivalent to a working iMessage channel.
- `space.send()` is the portable default for reliable delivery; Photon docs warn `message.reply()` may no-op on platforms without thread support. Prefer `space.send()` unless intentionally using a supported threaded response.
- Process may need provider-specific setup or webhook configuration; follow actual Photon docs for SDK version chosen.
- Use streaming/long-lived worker hosting (VPS/systemd or container with restart policy). **Do not** place `for await (... of app.messages)` inside a Vercel serverless handler.
- Map each platform's **verified sender identity** to canonical `users.id` using the database; senders do not control that mapping.
- Store and check `provider_event_id` to survive stream retries/replays.
- Default first release to **one-to-one DMs**; block group contexts from accessing an individual user's private memory unless explicit group authorization has been designed.

Photon references: https://github.com/photon-hq/spectrum-ts · https://photon.codes/docs/spectrum-ts/introduction · https://photon.codes/docs/spectrum-ts/reactions-and-replies

## 10. Cross-channel account linking contract

- Generate code with crypto-secure random bytes (≥128 bits entropy), base64url; display once; store only salted/hashed verifier, source UUID, expiry ≤10 minutes.
- A logged-in web session or verified linked messaging identity requests `/link` to create code.
- Target channel receives `/link <code>` or equivalent natural language. Verify the platform sender via Photon; never accept claimed Telegram username or iMessage number from free text.
- Require confirmation by source identity through verified Web UI or original messaging channel; link only after confirmation. Mark token used atomically.
- Collision/conflict: if target already has meaningful independent memories, **do not auto-merge** Walrus namespaces. Prompt for manual resolution; support new tester linking flow from a clean target identity.
- Rate-limit attempts and expire codes; log only hash/token ID, never the raw code.
- After linking, all channels resolve to the same canonical `user_id` and `namespaceFor(userId)`.
- Test token replay, wrong account, expired token, two simultaneous redemptions, and unauthorized memory query.

|---|---|---|---|
| `/api/chat` | POST | Session text → response, cited Walrus sources, save status | Server-resolved cookie; CSRF/origin check, rate limit, body length |

| `/api/link/confirm` | POST | Approve target claim | Bound source identity; atomic token consumption |
| `/api/memory/status` | GET | Confirm tracked jobs/blob counts for *current* user | No PII cross-user leak |
| `/api/health` | GET | Liveness; optional safe service-readiness indicators | Never expose secrets / privileged account data |

Example successful `/api/chat` body shape (illustrative product-owned interface, **not** Walrus SDK response):

```json
{
  "answer": "Based on what you told me, the quieter option may suit you better.",
  "memorySources": [
    {"blobId": "<actual blob ID>", "reason": "You prefer quiet rooms after a noisy stay."}
  ],
  "memorySave": {"state": "completed", "count": 1},
  "sessionId": "<server-issued id>"

```

Only emit `memorySources` if they were **really returned by Walrus for that authorized user**. They must never be fabricated from assistant reasoning.

## 12. Test matrix

### Unit / component

- `UT-01`: fact extraction ignores secrets/sensitive info and model guesses.
- `UT-02`: exact matching namespace for same user; different namespace for different user.
- `UT-03`: memory status `pending/failed/done` accurately maps to UI.
- `UT-04`: superseded blob IDs excluded; new fact prioritized.
- `UT-05`: prompt requires grounding and states no live availability.
- `UT-06`: expired/reused account-link token rejected.
- `UT-07`: duplicate provider message IDs do not cause duplicate saves/replies.

### Integration (live; **not mock**)

- `IT-01`: Mainnet memory write completes with blob ID (record relayer endpoint, account ID, timestamp).
- `IT-02`: new conversation/process recalls fact using same user UUID.
- `IT-03`: wrong user's namespace returns no fact from user A.
- `IT-04`: changed preference is reflected after new session.
- `IT-05`: real Telegram inbound/outbound round trip.
- `IT-06`: real Photon Cloud iMessage inbound/outbound round trip.
- `IT-07`: linked web ↔ Telegram ↔ iMessage context survives channel switch.
- `IT-08`: 3 real testers each show 10 distinct completed blobs and meaningful recalled fact.

### Recovery / fault handling

- `FT-01`: DeepSeek timeout → friendly temporary failure; don't fabricate reply.
- `FT-02`: MemWal 401 → operator-visible configuration error, not a fake saved notification.
- `FT-03`: Walrus save accepted but not indexed → pending status until authoritative completion.
- `FT-04`: repeated Photon delivery → only one app operation.
- `FT-05`: database temporarily down → no guest-to-other-user fallback namespace.

**Live tests must not be described as passed until they have actually been run.** Include exact results in README/evidence once implementation exists.

## 13. Performance, cost, safety and observability

- **Performance:** show typing/loading indicators and service timeouts; no made-up SLA. Track p50/p95 response latency in test logs if feasible.
- **Token/cost control:** short system prompt, ≤8 relevant memories, short current-session history, capped response tokens and extraction facts per turn; log usage totals without private text.
- **Rate limits:** user-based and channel-based; cap input length (e.g., 4,000 chars), reject large attachments in MVP, back off provider 429.
- **Privacy:** secrets only in server environment; privacy notice before testing; content stays in encrypted MemWal relayer flow per provider docs; explain app-operator custodial key model.
- **Log fields:** `trace_id`, `app_user_hash`, `namespace_hash` (or restricted namespace), `channel`, `model_id`, `memory_job_id`, `blob_id`, `save_status`, `retrieval_count`, `http_status`, latency. **Never log** raw private messages, keys or authorization tokens in production.
- **Service health:** startup checks for required vars, DB ping, MemWal `health()`, Photon init; auto-restart worker; graceful shutdown to avoid event loss.
- **Deployment rollback:** keep previous web release/worker version; migrations additive; do not reset production user data to repair demo.

## 14. Deployment and verification procedure

1. Provision Postgres and apply schema; test connection. Keep short-lived message retention cleanup scheduled or omit persisted transcripts.
2. Create a production Walrus Memory account, delegate key, and session-specific dedicated wallet as required. Check account environment and Mainnet relayer.
3. Verify DeepSeek API key with one `deepseek-flash` completion; document exact model ID.
4. Create Photon Spectrum Cloud project, configure iMessage line and Telegram bot provider, record **public contact instructions** only (never credentials).
5. Deploy web UI/route handlers to Vercel or Node host. Ensure all secrets are server-side.
6. Deploy Spectrum worker to always-on VPS/container with `systemd` or similar restart policy; configure TLS/outbound connectivity as demanded by Photon.
7. Run live smoke tests before recruiting testers; capture source IDs, versions, environment, returned blob IDs.
8. Have 3 real users interact and return after a fresh session; count distinct completed Mainnet blobs per user.
9. Sanitize and publish README + evidence; never make the demo depend on an unavailable private tunnel.
10. Publish article/X, external promo, and submit both forms before close.
